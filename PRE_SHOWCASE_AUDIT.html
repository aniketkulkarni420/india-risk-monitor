P0 · Showcase blockers (4)

P0INFRA-01

CI ingest is effectively dead — 88% of runs cancelled

The concurrency block I added in PR #10 (to fix the May-25 push race) overcorrected. With many cron triggers firing close together and cancel-in-progress: false, GitHub still cancels queued runs when a newer one arrives — so runs cancel each other in a storm.

last 25 ingest runs: 22 cancelled · 2 success · 1 failure most recent SUCCESS: 2026-05-27 05:56 UTC (45.9h ago) live bundle age: 39.5h

The irony, owned: the push race I "fixed" dropped ~1 run occasionally. This concurrency block drops 22 of 25. Net data freshness is now worse than the bug it replaced.

Suggested fix: Remove the concurrency: irm-data-push block from all 5 workflows. The git pull --rebase + 3-attempt retry on push (also added in PR #10) already solves the push race without serializing/cancelling runs. The concurrency block was belt-and-suspenders that became a noose. Verified the rebase-retry is present in ingest.yml.

P0DATA-01

Hormuz manual override expired — will revert to the known-bad value

The override pinning Hormuz to 12 transits/day (the validated crisis figure) expired 2026-05-28. The live bundle still shows 12 only because it's 39.5h stale. The next successful ingest will run the parser, which reads the hormuz-watch-2 endpoint that counts Gulf port presence (~148) not strait transits — reverting to "all normal" during an active closure.

override: value 12 · expires 2026-05-28 · EXPIRED 1.2d ago live now: 12 (frozen, stale bundle) · verification_state: source_pending

Suggested fix: Re-issue the override with a longer expiry (or until the layered Google-News + multi-tracker parser is confirmed live and accurate), and confirm today's actual transit figure from Windward/Lloyd's before pinning.

P0DATA-02

INR/USD = 95.26 — verify before showing (consistent but historically extreme)

The dashboard shows INR/USD at 95.26. This is NOT a one-off scrape glitch — the history is a smooth series from TradingEconomics across 8 readings. But it's an ~11% depreciation from the 83–86 range, which would be the weakest INR ever by a wide margin. Either the simulated-2026 crisis genuinely pushed it there, or TradingEconomics' india/currency page is being misread (e.g. a forward/NDF quote, not spot).

2026-05-14 95.604 2026-05-20 96.483 2026-05-15 95.803 2026-05-21 96.037 2026-05-18 96.276 2026-05-22 95.552 2026-05-19 96.718 2026-05-25 95.256 ← source: tradingeconomics.com/india/currency

Suggested fix: Human eyeball against a second source (RBI reference rate, XE, Google). If 95 is wrong, the te_inr_v1 selector is grabbing the wrong figure — a wrong headline FX rate is instant credibility death in a demo. If 95 is intentional crisis-fiction, leave it but be ready to explain.

P0DATA-03

GST unit inconsistency — lakh-crore vs crore mixed in history

The GST history mixes units: earlier rows are in lakh-crore (1.89 = ₹1.89 lakh cr) and the latest is in crore (243000 = ₹2.43 lakh cr). Any MoM/YoY/sparkline computed across this jump is mathematically garbage (1.89 → 243000 = +12.8 million %). Also 243,000 cr monthly is high vs the typical 170–210K — possibly a stale or annual figure (the parser was previously failing on "GSTN xlsx 71 days old").

2026-01-30 1.9932 (lakh-crore) 2026-02-28 1.89 (lakh-crore) 2026-05-01 243000 (crore) ← unit switch · breaks trend math

Suggested fix: Normalise the history to one unit (crore), backfill-convert the lakh-crore rows, and confirm 243,000 is a real monthly figure not an annual/cumulative. Re-run sparkline sanitiser after.
